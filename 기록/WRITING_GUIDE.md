## 1. 원고 유형 구분 — 신규 작성 vs 리포맷 (중요)

작업을 시작하기 전에 반드시 둘 중 어느 유형인지 정한다. 아래 2~10장의 "재구성한다" "새 예제를 만든다" "요약한다" 류 규칙은 **유형 B에만** 적용된다. 유형 A에 적용하면 원고가 파괴된다 — 실제로 C# 01 작업에서 이 구분이 없어서 사용자가 이미 작성한 docx 원고를 요약·재구성·임의 보강해버린 사고가 있었다.

| 유형 | 언제 | 무엇을 하는가 |
| --- | --- | --- |
| **A. 리포맷** | 사용자가 이미 완성한 원고(docx, 기존 글 등)를 블로그로 옮길 때 | 원문 그대로 두고 **양식만** 입힌다 |
| **B. 신규 작성** | 강의 PDF·링크 등 참고 자료를 바탕으로 **새 글**을 쓸 때 | 2~10장의 재구성·요약·새 예제 규칙을 그대로 적용 |

작업을 맡길 때 어느 쪽인지 애매하면 진행 전에 물어본다.

### 유형 A — 절대 하지 않는 것

- 문장 재서술·요약·축약. 표·목록의 항목 수를 줄이는 것도 포함 — 예를 들어 버전 이력표는 있는 그대로 전체 유지한다.
- 섹션 순서 변경, 섹션 병합·분리, 섹션 이름 임의 변경.
- 원본에 있던 이미지·다이어그램을 다른 것(자체 제작 mermaid 등)으로 교체.
- 원본에 없는 예제·표·prompt 박스·"자주 하는 실수" 등을 임의로 추가.
- 2~10장의 "재구성" "새 예제 필수" "요약" "출처 미표기" 규칙 적용 — 이 규칙들은 유형 B 전용이다.

### 유형 A — 하는 것 (양식만)

- 제목 계층 → 마크다운 헤딩. 원본이 H3보다 깊으면(예: "1.2.1" 같은 3단계 소제목) 새 H4를 만들지 않고 **볼드 리드 문장**으로 표현한 뒤, 이 처리가 맞는지 사용자에게 확인받는다.
- 표·목록 → 마크다운 표·불릿으로 형식만 변환. 정보량은 그대로.
- 이미지 → 원본에 있던 위치 그대로 유지. 대체 텍스트(alt)만 새로 작성한다(원본 docx엔 없던 값이라 이건 불가피한 추가).
- front matter, 카테고리/태그, 파일명 규칙(3~4장) — 이건 양식이므로 그대로 적용한다.
- `## 학습 목표` `## 정리` `### 핵심 코드 요약` 같은 **구조 스캐폴드**는 넣는다 — 이건 콘텐츠가 아니라 블로그 틀이다. 단, 항목은 실제 본문 헤딩을 나열한 것이어야 한다. 창작 금지.

### 유형 A에 자료를 보강하고 싶을 때

8.5장 중첩 처리 절차를 따르되, 유형 A는 **더 엄격하다.** 유형 B에 있는 "원본에 없는 신규 항목이면 승인 없이 바로 삽입" 예외가 유형 A에는 없다. 무엇을 어디에 더할지 표로 제시하고, **반드시 승인받은 뒤에만** 반영한다. 승인 전에는 초안에 아무것도 넣지 않는다.

## 2. 글의 성격

> 이 장부터 5장까지는 **유형 B(신규 작성)** 기준이다. 유형 A(리포맷)는 1장을 따른다.
{: .prompt-warning }

포트폴리오용 학습 기록이다. 강의 요약본이 아니다.

| 쓰는 것 | 안 쓰는 것 |
| --- | --- |
| 내가 이해한 순서로 재구성한 설명 | 강의 목차 그대로 복사 |
| 실제로 돌려본 코드와 실제 출력 | 실행해보지 않은 코드 |
| 실제 컴파일러가 내는 오류 메시지 | "오류가 날 수 있습니다" 식 서술 |
| 개념 하나당 최소 예제 하나 | 원본 자료의 예제 그대로 |
| 그 개념의 예외·실수 사례 | 개인 실험 후기 / 학습 일지 |
| 핵심만 남긴 짧은 설명 | 알고 있는 것 전부 나열 |

**종합 예제는 넣지 않는다.** 개념별 최소 예제로 대체한다.

**학습 일지형 섹션도 넣지 않는다.** `직접 해보며 확인한 것` 같은 개인 기록 섹션은 쓰지 않는다.
개념 설명에 필요한 **예외 코드**와 **실수 사례**만 해당 개념 아래에 붙인다.

### 예제 규칙

**원본 자료의 예제를 그대로 쓰지 않는다.** 같은 개념을 설명하는 **새 예제**를 만든다.

- 예제 소재는 게임 개발 쪽으로 통일한다 (체력, 점수, 아이템 개수, 메뉴 출력 등).
  시리즈 전체에서 소재가 이어지면 글이 하나의 흐름으로 읽힌다.
- 예제는 **그 개념 하나만** 보여준다. 아직 안 배운 문법이 섞이면 예제가 아니라 문제다.
- 코드는 짧을수록 좋다. 개념 예제 3~6줄, 비교 예제는 2줄이면 충분한 경우가 많다.
- 예제를 만들었으면 **반드시 실행해서 결과를 붙인다.** 머릿속 출력은 쓰지 않는다.

원본 예제를 그대로 써야만 하는 경우 (관용 코드 등)는 예외다. 예: `Console.WriteLine("Hello, World!");`

### 예외 코드 규칙

개념 예제 외에 추가로 쓸 수 있는 코드는 **그 개념의 예외 사례**뿐이다.

- 규칙이 적용되지 않는 경우, 결과가 달라지는 경우, 컴파일이 안 되는 경우.
- 예) `WriteLine()`을 인자 없이 호출 / 세미콜론 누락 / 대소문자 오타
- 예외 코드에는 **주석으로 무엇이 다른지** 표시한다.

```csharp
Console.WriteLine("Hello")   // 오류 - 세미콜론 누락
```

개인 실험 기록("돌려봤더니 이랬다")은 쓰지 않는다. 예외 자체를 개념의 일부로 서술한다.

### 인용·출처 정책

**참고한 강의 자료·PDF·링크를 본문에 출처로 제시하지 않는다.** 예시와 필요한 내용만 차용해 내 문장으로 다시 쓴다.

- `## 참고` 섹션은 **기본적으로 넣지 않는다.**
- 예외: 독자가 실제로 더 읽어야 하는 **공식 문서**(Microsoft Learn 등)만 링크한다. 없으면 섹션 자체를 생략.
- 강의 자료 원문을 옮기지 않으므로 인용 표기도 필요 없다. 대신 **전부 재서술**이 전제다.

### 분량 기준

핵심 설명 위주. 길이로 승부하지 않는다.

| 단위 | 기준 |
| --- | --- |
| 글 전체 | 스크롤 기준 5~8분 분량 |
| H2 섹션 | 4~8개 |
| 개념 설명 문단 | 2~5줄. 넘으면 표나 불릿으로 쪼갠다 |
| 코드 블록 | 3~6줄 |

**한 문단에서 한 가지만 말한다.** 배경 설명이 길어지면 `.prompt-info` 박스로 내리거나 잘라낸다.

## 3. 파일 / 경로 규칙

```
_posts/2026-08-30-csharp-01-intro.md          # 글
assets/img/posts/csharp-01-intro/vs-install-1.png   # 그 글의 이미지
```

- 파일명: `YYYY-MM-DD-csharp-NN-slug.md` — 소문자, 하이픈, **영문만**
- `NN`은 시리즈 순번(01, 02, …). 순번이 URL과 목차 정렬을 잡아준다.
- 이미지 폴더명 = 글 slug와 동일하게 맞춘다. 섞이면 관리 불가.
- 이미지 파일명도 영문. 한글 파일명은 URL 인코딩되어 깨진다.

## 4. Front matter 규칙

```yaml
---
title: "C# 02 — 첫 번째 프로그램 작성하기"
date: 2026-08-30 21:00:00 +0900
categories: [C#, 문법기초]
tags: [csharp, console, writeline, 최상위문]
math: false
mermaid: false
comments: true
---
```

- `title` — `C# NN — 제목` 형식 고정. 구분자는 em dash(`—`).
- `date` — 시각과 `+0900` 필수. 시각을 빼면 같은 날 글의 순서가 뒤집힌다.
- `categories` — **최대 2단계.** Chirpy 제약. `[대분류, 소분류]`
- `tags` — 3~6개. 소문자 영문 우선, 한국어 개념어는 그대로.
- `math` / `mermaid` — 실제로 쓸 때만 `true`. 켜두면 불필요한 스크립트가 로드된다.

### 카테고리 체계

| 대분류 | 소분류 | 용도 |
| --- | --- | --- |
| `C#` | `입문` | 기존 인트로 글 |
| `C#` | `문법기초` | 이번 시리즈 (변수, 연산자, 제어문 …) |
| `C#` | `객체지향` | 클래스 이후 |
| `유니티` | `입문` / `스크립팅` | |
| `알고리즘` | `입문` / `자료구조` | |

새 소분류를 만들기 전에 이 표를 먼저 갱신한다. 소분류가 무한정 늘면 분류 기능이 죽는다.

## 5. 본문 구조 (고정)

```
## 학습 목표          이 글에서 다루는 항목 3~5개
---
## 개념 A            설명 → 코드 → 실행 결과
  ### 자주 하는 실수   (있을 때만) 그 개념에서 나오는 실수
## 개념 B            (반복)
---
## 정리              불릿 3~5개
### 핵심 코드 요약     표
## 참고              (선택) 공식 문서가 있을 때만
```

- H1(`#`)은 쓰지 않는다. `title`이 H1이다. 본문 최상위는 H2.
- H4 이하는 쓰지 않는다. TOC가 지저분해진다.
- `---`(수평선)으로 도입부 / 본문 / 마무리 3덩어리를 나눈다.
- 개인 기록 섹션(`직접 해보며 확인한 것` 등)은 두지 않는다.
- 동기 설명 섹션(`왜 배우는가` 등)도 두지 않는다. 도입은 `## 학습 목표` 하나뿐.

### 학습 목표는 "무엇을 공부하는가"로 쓴다

`## 학습 목표`는 **이 글에서 다루는 항목의 목록**이다. 동기·필요성은 쓰지 않는다.
도입부는 이 섹션 하나로 끝낸다. 별도의 동기 설명 섹션은 두지 않는다.

| 쓴다 | 안 쓴다 |
| --- | --- |
| 다루는 대상을 명사구로 | "~의 필요성을 이해한다" |
| 본문 H2와 1:1로 대응 | 본문에 없는 항목 |
| 3~5개 | 본문 H2를 전부 나열 |

```markdown
## 학습 목표

- `Console.WriteLine`과 `Console.Write`의 차이
- 문(statement)과 세미콜론
- 최상위문과 `Main` 메서드
```

동기 유발 문구("왜 중요한지 알아봅니다")는 넣지 않는다. 항목만 적는다.
체크박스(`- [ ]`)는 쓰지 않는다. 목표 달성 체크가 아니라 **목차 성격**이다.

학습 목표 다음은 바로 첫 개념 H2다. 서론을 두지 않는다.

### 실수 사례는 개념 아래에 붙인다

`## 자주 하는 실수`를 글 끝에 몰아두지 않는다. **그 실수가 나오는 개념 바로 아래**에 붙인다.
독자가 개념을 읽은 직후에 보는 것이 맞고, 글 끝에 모으면 어느 개념 얘기인지 다시 찾아야 한다.

원본 강의의 주의사항·오류 항목을 다듬어서 해당 개념 하위로 분배한다.

| 실수 건수 | 형태 |
| --- | --- |
| 1건 | `.prompt-warning` 박스 한 개 |
| 2건 이상 | `### 자주 하는 실수` + 표 |

```markdown
## 문(statement)과 세미콜론

...개념 설명...

### 자주 하는 실수

| 잘못된 코드 | 오류 코드 | 원인 |
| --- | --- | --- |
| `Console.WriteLine("Hi")` | `CS1002` | 세미콜론 누락 |
| `console.WriteLine("Hi");` | `CS0103` | 대소문자 틀림 |
```

- 오류 코드(`CS1002` 등)와 **컴파일러가 실제로 내는 메시지**를 적는다. 검색 유입 재료가 된다.
- 실수 사례가 없는 개념에는 이 H3를 만들지 않는다. 억지로 채우지 않는다.

## 6. Chirpy 문법 치트시트

### 알림 박스

```markdown
> 참고 정보.
{: .prompt-info }

> 유용한 팁.
{: .prompt-tip }

> 주의할 점.
{: .prompt-warning }

> 하면 안 되는 것.
{: .prompt-danger }
```

박스 뒤 `{: .prompt-* }`는 **인용문 바로 다음 줄, 빈 줄 없이** 붙여야 적용된다.

### 코드 블록

````markdown
```csharp
Console.WriteLine("Hello");
```
````

- 언어 태그 필수: `csharp`, `text`, `bash`, `yaml`, `json`
- 실행 결과는 `csharp`가 아니라 **`text`**로 감싼다. 하이라이팅이 틀어지지 않는다.
- 파일 이름을 보여줄 땐 첫 줄에 `// Program.cs` 주석.

### 이미지

```markdown
![Visual Studio 워크로드 선택 화면](/assets/img/posts/csharp-01-intro/vs-workload.png){: width="700" }
_Visual Studio Installer에서 .NET 데스크톱 개발 선택_
```

- 경로는 `/assets/`로 시작하는 **절대 경로**.
- `alt` 텍스트를 반드시 쓴다 (SEO + 접근성 + 이미지 깨졌을 때 확인용).
- 바로 다음 줄 `_기울임_`이 캡션으로 렌더된다.
- 스크린샷은 `width="700"` 기본. 다이어그램은 생략 가능.

### 파일 경로 표기

```markdown
`_config.yml`{: .filepath }
```

### 표

```markdown
| 구분 | 저수준 언어 | 고수준 언어 |
| --- | --- | --- |
| 예시 | 기계어, 어셈블리어 | C#, Python, Java |
```

3열 이상이면 모바일에서 가로 스크롤된다. 4열을 넘기지 않는다.

## 8. 추가 자료 편입 규칙

글을 쓰는 도중이나 발행 후에 **링크·PDF·강의 자료를 주면서 "이 내용 넣어줘"** 하는 경우의 처리 규칙.

자료는 **차용 대상**이지 인용 대상이 아니다. 필요한 예시와 내용만 뽑아 재서술하고, 출처는 본문에 남기지 않는다.
위치는 매번 상의하지 않고 아래 표로 자동 판단한다. **단, 중첩이 생기면 반드시 물어본다 (8.5 참고).**

### 판단 기준 한 줄

> **그 자료가 답하는 질문이 이미 본문에 있는가?**
> 있으면 → 그 섹션 안. 없으면 → 새 H2를 만들어 난이도 순서에 끼워 넣는다.

### 자료 유형별 삽입 위치

| 자료 유형 | 들어갈 위치 | 형태 |
| --- | --- | --- |
| 개념의 정의·스펙 보강 | 해당 개념 H2 본문 | 재서술해서 문단에 녹임. 출처 링크 없음 |
| 버전·지원 범위 (예: Unity는 C# 9.0까지) | 해당 개념 바로 뒤 | `.prompt-warning` |
| 배경·역사·여담 | 해당 개념 바로 뒤 | `.prompt-info` |
| 단축키·실무 팁 | 해당 개념 바로 뒤 | `.prompt-tip` |
| 하면 안 되는 것 | 해당 개념 바로 뒤 | `.prompt-danger` |
| 오류 사례 / 오류 코드 | **해당 개념 아래** `### 자주 하는 실수` | 표에 행 추가. 없으면 H3 신설 |
| 비교 정보 (A vs B) | 기존 비교표 | 열 또는 행 추가 |
| 코드 예제 | 해당 개념의 코드 블록 | **새 예제로 다시 만들어** 교체/추가, 실행 결과 필수 |
| 개념의 예외 사례 | 해당 개념 본문 끝 | 예외 코드 + 주석. 1건이면 `.prompt-warning` |
| 어디에도 안 붙는 새 개념 | **새 H2** | 아래 순서 규칙대로 위치 결정 |
| 공식 문서 링크 | `## 참고` | 독자가 실제로 더 읽어야 할 때만 |
| 그 외 참고 링크 | — | 넣지 않는다. 내용만 차용 |

### 8.5 중첩 처리 — 임의로 병합하지 않는다

추가 자료가 **강의 원본과 겹치는 내용**을 담고 있으면, 합치기 전에 **반드시 물어본다.**
알아서 병합하면 글이 원본보다 길어지고 같은 말이 두 번 나온다.

**절차**

1. 중첩 구간을 먼저 표로 뽑아 제시한다.

   | # | 강의 원본 | 추가 자료 | 겹치는 내용 | 추가 자료에만 있는 것 |
   | --- | --- | --- | --- | --- |
   | 1 | 출력 메서드 | 3장 콘솔 출력 | `WriteLine` 기본 사용 | `Console.WriteLine` 서식 지정 |

2. 구간마다 아래 4개 중 하나를 고르게 한다.

   | 선택 | 처리 |
   | --- | --- |
   | **A. 기존 유지 + 없는 것만 추가** | 겹치는 서술은 원본 것만 남기고, 추가 자료의 신규 항목만 붙임 (기본값) |
   | **B. 추가 자료로 교체** | 추가 자료 쪽 설명이 더 정확하면 해당 구간을 갈아끼움 |
   | **C. 강조** | 양쪽에 다 있으니 중요한 개념 → 박스나 표로 끌어올려 강조 |
   | **D. 제외** | 이 글의 범위 밖 → 버리거나 다음 글로 이월 |

3. 답을 받은 뒤에만 본문에 반영한다.

> 물어보지 않고 병합해도 되는 유일한 경우: 추가 자료의 내용이 **원본에 전혀 없는 신규 항목**일 때.
> 이때는 위 자료 유형표대로 바로 삽입한다.
{: .prompt-info }

### 새 H2를 끼워 넣는 순서 규칙

본문 H2는 항상 이 난이도 흐름을 유지한다. 새 개념은 이 흐름에서 자기 자리를 찾는다.

```
쓰는 법 → 문법 규칙 → 구조 → 빌드/실행 → 오류/디버깅
```

예) "주석" 자료가 들어오면 → `문법 규칙` 구간, 세미콜론 섹션 뒤.
예) "디버거 중단점" 자료가 들어오면 → `빌드/실행` 뒤.

### 삽입 후 반드시 동기화할 곳

새 H2를 추가했다면 아래 3곳이 같이 바뀌어야 한다. 하나라도 빠지면 글이 어긋난다.

- [ ] `## 학습 목표` — 항목 추가
- [ ] `## 정리` — 불릿 추가
- [ ] `### 핵심 코드 요약` — 코드가 늘었으면 행 추가
- [ ] 10장 개념 소유권 대장 — 새 개념 등록

### 인용 원칙

- 원문을 그대로 붙여넣지 않는다. **전부 내 문장으로 재서술한다.**
- 강의 자료·PDF·링크는 **본문에 출처로 남기지 않는다.** 예시와 필요한 내용만 차용한다.
- 예제는 원본 것을 쓰지 않고 새로 만든다 (2장 예제 규칙).
- 공식 문서만 예외적으로 `## 참고`에 링크한다. 링크할 게 없으면 섹션을 생략한다.
- `.prompt-*` 박스는 **연속 3개 이상 금지.** 넘어가면 본문 문단으로 내린다.

## 10. 글 간 중복 방지 — 개념 소유권 대장

**한 개념은 한 글에서만 설명한다.** 다른 글에서 그 개념이 필요하면 설명을 반복하지 않고 **한 줄 요약 + 링크**로 넘긴다.

### 규칙

| 상황 | 처리 |
| --- | --- |
| 이 글이 그 개념의 **주인**이다 | 여기서 제대로 설명한다 |
| 다른 글이 주인인데 **언급만 필요**하다 | 한 줄 요약 + 해당 글 링크. 코드 예제 반복 금지 |
| 다른 글이 주인인데 **설명 없이는 진행이 안 된다** | 2~3줄까지만 허용 + 링크. 그 이상이면 글 순서를 바꾼다 |
| 어느 글의 주인인지 정해지지 않았다 | 아래 대장에 먼저 등록하고 쓴다 |

허용되는 최소 참조 형태:

```markdown
변수는 값을 담아두는 이름표입니다. 자세한 내용은 [C# 03 — 변수와 자료형](/posts/csharp-03-variable/)에서 다룹니다.
```

> 같은 개념을 두 글에서 설명하고 있으면 **둘 중 하나는 지운다.** 남길 쪽은 대장에 적힌 주인 글.
